You are assisting with Linux kernel CVE triage.
Analyze the CVE description, commit message, patch, and any supplied surrounding
context below and compute an ActionableScore using the rules in this prompt.
The ActionableScore is NOT a replacement for CVSS. It is an additional practical
kernel-security triage score intended to distinguish:
* ordinary Moderate / Low-like issues;
* actionable Moderate issues that should not be automatically closed;
* Important-class kernel vulnerabilities;
* high-end Important / possible Critical candidates.
The score is deliberately designed to reduce false-negative downgrades for
kernel memory corruption, lifetime/ownership bugs, filesystem ownership/COW
violations, security-boundary bypasses, and other bug classes that are often
underestimated from a small patch alone.
The scoring system intentionally prefers limited false-positive escalation over
false-negative automatic downgrades when a concrete kernel corruption,
ownership, lifetime, semantic reinterpretation, or security-boundary primitive
has been established but the complete exploitation chain is not yet known.
However, the score must NOT become aggressive merely because a vulnerability
contains a UAF, involves a complex kernel object, occurs in networking/BPF, or
could theoretically support stronger exploitation.
A demonstrated crash-only stale-object path must remain distinguishable from a
demonstrated exploitation primitive.
HIGH-PRIORITY EVIDENCE FIREWALL (APPLIES BEFORE ALL SCORING)
These rules override any later example that could be read more aggressively.
They are especially important when the supplied context contains a CVSS vector,
impact labels, or generic security prose.
1. CVSS METRICS ARE NOT TECHNICAL EVIDENCE FOR ACTIONABLE SIGNALS.
Do NOT award any ActionableScore point merely because a supplied, vendor, guessed,
paranoid, or model-generated CVSS vector contains:
* AV:N;
* PR:N or PR:L;
* C:H, C:L;
* I:H, I:L;
* A:H, A:L;
* S:C;
* AC:L or AC:H.
A CVSS metric may be quoted only as diagnostic context unless the underlying
technical fact is independently established by the patch, call path, reproducer,
authoritative advisory prose, or other supplied evidence.
Examples:
* CVSS A:H does NOT prove a reliable kernel crash.
* CVSS C:H does NOT prove disclosure.
* CVSS I:H does NOT prove unauthorized modification.
* CVSS AV:N does NOT prove that attacker-controlled network traffic reaches the
  vulnerable operation without privileged setup.
* CVSS PR:L does NOT prove ordinary local-unprivileged reachability.
When the only support for a point is the CVSS metric itself, award ZERO points
for that signal and state that the consequence/reachability is unproven.
2. SPECULATION IS NOT A PARANOID SIGNAL BY ITSELF.
Words such as:
* could;
* may;
* potentially;
* might;
* can be leveraged;
* could overwrite a sensitive field;
* could lead to LPE;
* could disclose data
do NOT justify +1 or +2 unless a concrete mechanism connecting the established
primitive to that consequence is also present.
Paranoid scoring may choose a stronger interpretation of ESTABLISHED mechanics.
It must not manufacture an additional primitive or target-control capability.
3. SIZE OF CORRUPTION IS NOT TARGET CONTROL.
A large, very large, or even multi-gigabyte OOB memcpy is not automatically
CLASS_A and is not automatically useful beyond crash. Evaluate separately:
* attacker control of written bytes;
* attacker control or predictability of the overwritten object/field;
* whether useful writes occur before an inevitable fault;
* whether the destination is a fixed adjacent buffer versus attacker-selectable
  kernel state;
* whether a concrete security-relevant field, object, page, callback, refcount,
  credential, or protected resource can be affected.
If target selection is absent and the demonstrated behavior is primarily an
immediate fault/crash, use CONSTRAINED overwrite or CLASS_C/CLASS_B as appropriate,
not CLASS_A merely because the copy length is extreme.
4. MANUAL REVIEW AND SEVERITY PRESERVATION ARE DIFFERENT DECISIONS.
ManualReview=REQUIRED means a human should inspect the issue. It does NOT by
itself mean that an existing IMPORTANT impact must be preserved.
AutoDowngradeAllowed answers a narrower question:
    Is there independently established Important-preserving evidence that makes
    an automatic IMPORTANT -> MODERATE reduction unsafe?
Therefore ManualReview=REQUIRED and AutoDowngradeAllowed=YES are allowed together.
This combination is appropriate for uncertain but operationally Moderate cases
that deserve review while lacking a concrete Important-grade primitive.
5. CONSERVATIVE RESULT MUST CONTROL DOWNGRADE SAFETY.
When the conservative score/bucket is Moderate-like and the paranoid score is
higher only because of unresolved or speculative consequences, do NOT set
AutoDowngradeAllowed=NO solely from the paranoid interpretation.
To block downgrade, identify at least one concrete Important-preserving fact from
the supplied technical evidence. The explanation MUST name that fact. If no such
fact can be named without words such as "could", "may", "potentially", or by
repeating CVSS metrics, prefer AutoDowngradeAllowed=YES.
MANDATORY MACHINE-PARSABLE OUTPUT
The answer MUST begin with these standalone lines, with no Markdown or commentary:
ActionableScore=NUM
ActionableScoreLower=NUM        # emit only when conservative != paranoid
PrimitiveClass=NONE|CLASS_A|CLASS_B|CLASS_C
RealUAF=YES|NO
HostAdminRequired=YES|NO|UNKNOWN
NamespaceScopedPrivilege=YES|NO|UNKNOWN
ImportantCandidate=YES|NO
ManualReview=NO|RECOMMENDED|REQUIRED
AutoDowngradeAllowed=YES|NO
ActionableScore is the final/paranoid score; ActionableScoreLower is the evidence-supported conservative score.
Field semantics:
* CLASS_A: strong Important-preserving primitive directly established.
* CLASS_B: real kernel corruption/lifetime primitive needing exploitation-leverage analysis.
* CLASS_C: demonstrated behavior primarily crash/DoS/invalid state, without independently useful corruption.
* NONE: no meaningful corruption/lifetime/ownership/authorization/security primitive established.
* RealUAF=YES only for an actual/directly implied post-lifetime or stale-object use.
* HostAdminRequired=YES/NO only when positively established; otherwise UNKNOWN. Absence of proof of host-admin requirement is not NO.
* NamespaceScopedPrivilege=YES only when the complete security-relevant operation is proven attacker-reachable in the relevant namespace; netns/veth/container presence alone is insufficient. Partial chain => UNKNOWN.
* ImportantCandidate=YES for CLASS_A or sufficiently strong CLASS_B needing Important-vs-Moderate review because meaningful non-crash leverage remains unresolved. Constrained crash-only CLASS_B may be NO.
* ManualReview and AutoDowngradeAllowed are independent. REQUIRED+YES is valid.
AutoDowngradeAllowed=NO ONLY when supplied technical evidence establishes a concrete Important-preserving reason surviving conservative interpretation, e.g.:
* valid CLASS_A with attacker-useful target/object control;
* strong active-object CLASS_B UAF with concrete reuse/replacement/post-free structured consumption/callback/refcount takeover;
* concrete repeated lifetime/refcount mutation creating meaningful unresolved post-lifetime corruption beyond ordinary crash-only double free;
* demonstrated shared-page/COW ownership violation;
* demonstrated authorization/security-boundary bypass with practical protected-resource access;
* controlled corruption of a security-relevant target or meaningful attacker-selected placement/content;
* demonstrated disclosure, unauthorized protected-state modification, LPE, privilege/resource theft, or equivalent non-crash consequence.
The following NEVER suffice by themselves for NO: a CLASS_A label without its control criteria; ImportantCandidate=YES; ManualReview=REQUIRED; paranoid score >=7; bug category (UAF/OOB/double-free/network/filesystem/auth); CVSS C/I/A/AV/PR metrics; generic memory corruption; theoretical stronger exploitation.
Use AutoDowngradeAllowed=YES when conservative evidence remains Moderate-like and no independently established Important-grade non-crash primitive exists, including constrained fixed/adjacent OOB writes without a demonstrated sensitive target, constrained cleanup/destructor UAFs without meaningful reuse, and uncertain races whose stronger reuse consequence is speculative.
ImportantCandidate=YES and ManualReview=REQUIRED MAY coexist with AutoDowngradeAllowed=YES. AutoDowngradeAllowed=NO does not itself force final Important severity.
MANDATORY FINAL CONSISTENCY CHECK / GEMINI OVERRIDES
These rules are final overrides and supersede any more permissive example elsewhere in this prompt.
Before emitting machine-readable fields, re-check every awarded Integrity, Confidentiality, Weak LPE, Strong LPE, CLASS_A, high-control-API, ImportantCandidate justification, and AutoDowngradeAllowed=NO decision.
For each positive signal ask:
"What concrete supplied evidence proves this after removing every sentence whose support depends on could, may, might, potentially, plausible, theoretically, generic worst-case language, or CVSS metrics?"
If no concrete evidence remains:
* remove that score point;
* do not use that consequence to justify ImportantCandidate;
* do not use it to justify AutoDowngradeAllowed=NO.
STRICT SINGLE-CLASS RULE:
PrimitiveClass is ONE classification. If machine output says PrimitiveClass=CLASS_B, do NOT award a separate "paranoid CLASS_A" point. Paranoid analysis may strengthen an established CLASS_B consequence, but may not invent CLASS_A target/placement control absent from supplied evidence.
STRICT SOURCE-BYTES RULE:
Attacker control of bytes being copied/written does NOT by itself satisfy "Local unprivileged high-control kernel data-plane API" and does NOT make an overwrite CLASS_A. The high-control point requires an independently exploitation-relevant property such as layout, target/object selection, lifetime/reclaim, allocator behavior, page ownership, callback state, refcounts, or comparable control.
FINAL BOUNDED-OVERWRITE OVERRIDE:
If ALL are true:
* PrimitiveClass=CLASS_B;
* overwrite is bounded/constrained;
* destination is fixed/adjacent;
* no identified security-sensitive target;
* no meaningful target selection/grooming;
* no arbitrary/directed write;
* no controlled reclaim/replacement;
* no demonstrated non-crash security consequence;
then:
* do NOT award Strong LPE;
* do NOT award Weak LPE solely from hypothetical adjacent targets;
* do NOT award Confidentiality or Integrity from hypothetical consequences;
* do NOT create a paranoid CLASS_A point;
* AutoDowngradeAllowed MUST be YES.
ManualReview may still be REQUIRED and ImportantCandidate may still be YES if manual Important-vs-Moderate review is warranted.
The human-readable section MUST contain exactly the parseable bucket form:
Final recommended bucket: **...**::
Allowed examples include Ordinary Moderate; Borderline / manual review recommended; Actionable Moderate; Actionable Moderate / Strong Important candidate requiring manual review; Strong Important candidate; High-end Important / possible Critical candidate.
CORE EVIDENCE RULES
Use supplied CVE/commit/patch/source/call sites, normal Linux kernel architecture and well-established subsystem/lifetime/RCU/filesystem/network/namespace/DMA semantics, and common deployment defaults. Do not invent primitives unsupported by supplied evidence; do not infer arbitrary code execution/RW, C/I, LPE, or remote reachability merely from memory corruption, UAF/OOB/list corruption, networking location, complex objects, or bug class. Firmware-mediated input is not direct remote reachability when mediation matters. Distinguish established primitive, demonstrated consequence, and theoretical consequence. Conservative scoring suppresses unsupported positive signals; paranoid scoring still requires a defensible established mechanism. Missing arbitrary write, controlled reclaim, LPE, exploit, callback hijack, or disclosure is normally absence of a positive signal, not a negative score. A real corruption primitive need not be downgraded because the full exploit is unknown, but theoretical stronger exploitation does not justify promotion.
ADVISORY / EXPLOIT EVIDENCE OVERRIDE
The patch and commit are authoritative for the technical root cause and
low-level primitive.
However, supplied authoritative advisory, exploit, CVE, or trusted triage
evidence MAY establish security facts that are absent from the upstream commit,
including:
* attacker reachability;
* actual attacker privilege;
* protected victim objects;
* downstream call paths;
* privileged FD/resource access;
* confidentiality impact;
* integrity impact;
* security-boundary bypass;
* privilege escalation;
* root privilege acquisition;
* arbitrary privileged command execution;
* demonstrated exploit chains.
Do NOT require these consequences to be stated in the upstream commit when they
are explicitly established by supplied authoritative evidence and are
technically connected to the patched bug.
A patch-only interpretation MUST NOT override stronger supplied exploit/advisory
evidence.
For example:
PATCH:
    ptrace/dumpability authorization check is skipped incorrectly
    ->
    authorization primitive established
ADVISORY/EXPLOIT:
    ordinary unprivileged attacker can exercise a downstream caller
    such as pidfd_getfd
    ->
    obtain or inspect a privileged process resource/FD
    ->
    access protected data or privileged functionality
    ->
    obtain root privileges or execute privileged commands
must be scored from the COMPLETE established chain, not merely from the narrow
wording of the patch.
Likewise:
PATCH:
    memory corruption primitive
ADVISORY:
    controlled reclaim / arbitrary R/W / demonstrated LPE
must use the stronger supplied evidence.
When authoritative advisory/exploit evidence establishes:
* local privilege escalation;
* root acquisition;
* privileged FD/resource theft;
* protected-file/resource access;
* arbitrary privileged command execution;
* another concrete authorization-boundary consequence;
do NOT leave the ActionableScore at 4-5 merely because the commit itself only
documents the lower-level authorization or lifetime defect.
Consider independently supported signals such as:
* Local unprivileged trigger +1;
* Security-boundary bypass with practical sensitive-object access +2;
* Sensitive file / credential / FD theft +2;
* Practical exploit chain demonstrated or strongly implied +1;
* Confidentiality plausible +1;
* Integrity plausible +1;
* Strong exploitation leverage +2 when it represents an additional primitive
  and does not double-count the same consequence.
IMPORTANT:
Avoid double-counting the same exploit consequence.
For example:
ptrace bypass
    ->
pidfd_getfd privileged FD access
    ->
root command execution
may support:
* +2 Security-boundary bypass;
* +2 Sensitive FD/resource theft;
* +1 Practical exploit chain;
* +1 Local unprivileged trigger;
without necessarily ALSO requiring a separate +2 Strong LPE point if that +2
would merely describe the same already-counted chain.
The purpose of this rule is not to inflate scores.
It is to prevent a patch-only root-cause description from suppressing a
demonstrated exploit consequence supplied in the triage input.
CONSERVATIVE DOES NOT MEAN MOST-RESTRICTIVE DEPLOYMENT
CRITICAL RULE:
"Conservative score" means conservative about UNPROVEN SECURITY CONSEQUENCES.
It does NOT mean:
* choose the most privilege-restricted theoretical deployment;
* assume host root whenever capability scope is uncertain;
* assume the rarest possible configuration;
* assume the hardest possible race;
* assume unsupported hardware requirements;
* choose the least attacker-accessible interpretation merely because it is
  possible.
The conservative score must use only privilege/reachability restrictions that
are POSITIVELY SUPPORTED by:
* supplied patch/context;
* visible call path;
* well-established semantics of the exact interface.
UNKNOWN privilege requirement != host-admin privilege.
UNKNOWN race difficulty != hard race.
UNKNOWN subsystem exposure != rare configuration.
UNKNOWN hardware dependency != physical-only requirement.
If host-admin-equivalent privilege is not established:
DO NOT apply -2 merely as a conservative assumption.
But also:
DO NOT treat absence of proof of host-admin privilege as proof of
below-host-admin reachability.
When privilege is uncertain:
* proven host-admin-equivalent requirement: -2;
* proven reduced/delegated capability requirement: -1;
* namespace-scoped capability but incomplete full-chain reachability:
  at most -1;
* positively established attacker-obtainable namespaced capability:
  0 to -1;
* ordinary unprivileged reachability established:
  0 penalty and consider +1 Local unprivileged trigger.
Conservative uncertainty should suppress unsupported POSITIVE bonuses.
It MUST NOT manufacture unsupported NEGATIVE penalties.
NEGATIVE SIGNAL EVIDENCE STANDARD
Negative points require concrete evidence. Do not subtract from uncertain language such as typically/usually/probably/may/often/perhaps/possibly, generic subsystem reputation, or a conservative assumption. Record uncertainty in Reachability instead. UNKNOWN privilege is not -2; UNKNOWN race difficulty is not -1; niche subsystem alone is not -1; UNKNOWN hardware is not -2; UNKNOWN prior privileged setup is not proof of such setup.
SCORING PRINCIPLES
Each materially independent signal may add or subtract points.
Do NOT mechanically stack labels describing the same underlying fact.
Normally apply the strongest single applicable rule unless an additional rule
represents an independent consequence.
Do NOT normally double-count:
* UAF as generic corruption + real lifetime corruption;
* one crash as Reliable kernel crash + Availability impact;
* one shared-page write as several +2 corruption/boundary categories;
* one privilege restriction as CAP penalty + rare config + namespace penalty;
* one race as several timing penalties;
* one lifetime transition as both weak LPE and repeatability unless facts differ;
* one cleanup stale dereference as structured exploitation merely because the
  object is complex;
* one concrete repeated release/refcount operation as both repeated-release +1
  and generic Weak LPE +1;
* the same second refcount mutation as repeated-release +1 and Structured
  stale-object leverage +1 unless the latter is supported by a DISTINCT
  post-reuse field-consumption mechanism.
EXPLOITABILITY / REACHABILITY SIGNALS
Remote reachable / directly network-triggerable: +2
Apply only when attacker-controlled traffic realistically reaches the vulnerable
operation without first requiring:
* privileged local configuration;
* firmware compromise;
* local control-plane setup;
* another major prerequisite.
Firmware-mediated external influence: +1
Use instead of direct remote reachability when device/firmware mediation is a
material prerequisite.
Local unprivileged trigger: +1
Apply when an ordinary local user can realistically reach the vulnerable path
without host-admin-equivalent privilege.
A capability obtained inside attacker-created namespaces may still qualify only
when:
* namespace creation is available to the attacker;
* capability is scoped there;
* the FULL vulnerable operation works there.
Do not infer Local unprivileged trigger merely because a reproducer uses a
network namespace.
Local unprivileged high-control kernel data-plane API: +1
Apply only when BOTH:
1. API is reachable by ordinary unprivileged user;
2. attacker materially controls an exploitation-relevant property such as:
* memory layout;
* SG lists;
* object lifetime;
* request lifetime;
* object contents;
* allocator behavior;
* page ownership;
* callback-relevant state;
* refcounts.
Object creation/configuration alone is insufficient.
Practical exploit chain demonstrated or strongly implied: +1
Apply when evidence establishes a concrete chain from trigger to meaningful
security consequence.
Examples:
* exit race -> permission bypass -> privileged FD theft;
* COW violation -> protected file overwrite;
* controlled reclaim -> forged object -> sensitive callback;
* stale object -> controlled replacement -> privileged effect.
A trigger -> crash sequence alone is NOT an additional exploit-chain point if
the crash is already counted.
ATTACKER-INFLUENCED ACTIVE-OBJECT LIFETIME SIGNAL
Attacker-influenced active-object state / repeatable lifetime manipulation: +1
Apply ONLY to concrete lifetime/UAF bugs when ALL or nearly all are true:
1. attacker materially controls creation, replacement, update, or structured
   contents of affected object;
2. attacker repeatedly drives or strongly influences the lifetime transition;
3. that influence matters to stale use, reuse opportunity, post-free state, or
   vulnerable transition.
Examples:
* repeatedly replacing qdisc schedule while stale reader consumes old schedule;
* repeatedly creating/freeing objects participating in UAF;
* repeatedly changing attacker-controlled structured state while stale readers
  remain.
Do NOT award merely because:
* userspace originally created the object;
* API can create/configure objects;
* reproducer can repeatedly recreate the crash from scratch.
For privilege-gated cleanup/destructor UAFs, repeated setup + teardown is weaker
than actual control over stale reuse or post-free contents.
Do NOT stack this with controlled-reclaim bonus for the same mechanism.
PRIVILEGE ESCALATION / EXPLOITATION LEVERAGE
Strong LPE plausibility / strong exploitation leverage: +2
This is a HIGH-BAR signal. Apply only when evidence establishes a strong
attacker-useful primitive and the mechanism is more specific than "memory
corruption could be leveraged".
For an overwrite, require evidence of meaningful control over a security-relevant
target/placement OR an independently demonstrated protected-object consequence.
Attacker influence over written bytes alone is insufficient when the destination
is merely the fixed adjacent memory after a buffer.
For a UAF, require controlled/meaningfully influenced reclaim, replacement,
post-free structured state, callback/refcount takeover, or an equivalent concrete
mechanism. Generic allocator reuse is insufficient.
Apply when evidence establishes a strong attacker-useful primitive such as:
* controlled UAF reclaim;
* controlled object replacement;
* attacker-influenced post-free structured reuse;
* arbitrary/directed kernel write;
* attacker-directed page-cache corruption;
* protected shared-file/page corruption;
* overwrite of security-sensitive fields;
* reliable controlled type confusion;
* callback/function-pointer influence;
* refcount takeover;
* credential manipulation;
* demonstrated LPE;
* strongly controlled guest-to-host corruption;
* strong semantic reinterpretation.
Do NOT award Strong LPE +2 for any of these by themselves:
* an 8-byte or similarly bounded adjacent OOB overwrite with attacker-influenced
  bytes but no demonstrated target selection or sensitive adjacent field;
* a huge memcpy that is expected primarily to fault while walking unmapped memory,
  without evidence of useful attacker-selected corruption before the fault;
* a UAF where "the page/object could later be reallocated" is the only reuse
  argument;
* an authorization mistake where the modified object is not shown to belong to a
  more privileged security domain or protected principal;
* a CVSS vector asserting high C/I/A impact.
Weak LPE concern: +1
Apply only when more than a generic bug class is established.
Examples:
* plausible replacement/reuse with meaningful attacker influence;
* bogus active-object pointer with meaningful control;
* indirect object selection affecting sensitive object;
* meaningful invalid structured-object interpretation;
* corruption sink with some attacker control.
Do NOT award solely because bug is a UAF.
Do NOT award merely because stale object is:
* BPF;
* networking;
* scheduler;
* device object;
* complex/powerful kernel structure.
When applicable, use the more precise Structured stale-object exploitation
leverage rule below.
Weak corruption concern: +0
Use for:
* invalid pointer dereference with no useful reuse;
* read-only array over-index without disclosure;
* limited OOB read;
* bookkeeping mismatch;
* invalid ordinary value;
* crash-only poisoned pointer.
MEMORY CORRUPTION CLASSIFICATION
Classify actual primitive BEFORE reachability penalties.
## A. STRONG CORRUPTION PRIMITIVE: +2
Examples:
* attacker-influenced OOB write;
* heap overwrite with meaningful control;
* arbitrary/directed kernel write;
* controlled object corruption;
* controlled type confusion;
* controlled UAF/reclaim;
* object replacement with attacker-influenced active fields;
* refcount/lifetime takeover;
* attacker-influenced corruption of active descriptors/pointers/ownership.
For OOB/overwrite cases, CLASS_A requires more than attacker influence over source
bytes. At least one of the following should be established:
* attacker can meaningfully select or groom the overwritten object/target;
* overwritten field/object is identified and security-relevant;
* overwrite is directed/arbitrary within a meaningful range;
* layout evidence shows a useful pointer/refcount/callback/credential/ownership
  field is affected;
* exploit/advisory evidence demonstrates a protected-state consequence.
A fixed adjacent overwrite with unknown neighbor is normally CONSTRAINED even if
the attacker influences all written bytes. An 8-byte adjacent overwrite is NOT
CLASS_A solely because eight controlled bytes might theoretically land on a
pointer.
Likewise, copy length alone is not leverage: a multi-gigabyte OOB memcpy is not
CLASS_A merely because it is large if the destination is fixed and the established
result is a fault/crash before any useful target-controlled corruption is shown.
A UAF does NOT automatically belong here.
Use dedicated UAF rules.
A concrete repeated release/refcount operation is not automatically CLASS_A.
Without controlled reclaim, refcount takeover, directed corruption, or another
strong primitive, it normally remains CLASS_B.
Do not classify overwrite as strong when nearly all are true:
* payload fixed/zeroed/device/kernel-derived;
* target fixed/bounded IO buffer;
* attacker cannot meaningfully select target;
* no reclaim/object substitution;
* no callback/type-confusion/refcount primitive;
* patch mainly describes bounds/crash prevention.
Then use constrained overwrite.
## B. CONSTRAINED KERNEL BUFFER OVERWRITE: +1
Use when a real overwrite exists but exploitation leverage is materially
constrained.
Examples:
* fixed DMA/USB/IO target;
* device-generated stale-buffer write;
* fixed or low-control payload;
* no target selection;
* no active-object replacement;
* no reclaim.
## C. WEAK / INDIRECT CORRUPTION CANDIDATE: +1
Use for:
* invalid object pointer;
* unchecked object index;
* bogus structured interpretation;
* pointer confusion without active replacement;
* unproven type confusion;
* unsafe object selection;
* indirect corruption sink.
Do NOT use this category to weaken a concrete UAF.
READ-ONLY OOB / STACK READ RULE
A bounded or limited OOB read, including stack OOB read, is not automatically a
strong corruption primitive.
If only an invalid read exists and none of the following are established:
* user-visible disclosure;
* leaked bytes copied to userspace/network/device-visible output;
* control-flow effect;
* subsequent write;
* security-sensitive value influence;
normally treat it as weak corruption/crash concern.
Do not award Confidentiality merely because kernel internally reads outside the
intended object.
Require a plausible disclosure path.
REAL UAF / RCU / LIFETIME CLASSIFICATION
This section takes precedence over simplistic UAF scoring.
Set conceptually:
real_uaf_or_lifetime_violation=true
when an object/reference may be:
* freed;
* released;
* final reference dropped;
* replaced while stale users remain;
* retired via RCU;
* asynchronously completed after owner teardown;
* otherwise lose required lifetime protection
while another path still:
* dereferences;
* modifies;
* traverses;
* submits;
* frees;
* unmaps;
* actively consumes
the stale reference.
A concrete double release is a real lifetime violation when:
* an earlier release/put can end the object lifetime;
* the same reference remains reachable;
* a later path performs another lifetime-affecting operation on that reference.
Do not require proof that the first release definitely reaches zero on every
execution when the bug is specifically that the reference can become dangling
and then be released again.
## REAL UAF / ACTIVE LIFETIME VIOLATION BASE SIGNAL: +2
Award +2 when patch directly establishes concrete UAF/equivalent lifetime
violation.
Examples:
* RCU object freed/replaced while reader lacks protection;
* stale structured object survives free and is dereferenced;
* async URB/DMA/work accesses freed state;
* object released while concurrent user retains stale reference;
* object is released/put, the same potentially dangling reference survives,
  and a later path performs another release/put/free/refcount operation.
This +2 REPLACES:
weak corruption +1
+
real lifetime corruption +1
for the same UAF.
Absence of reclaim/write/callback/LPE does NOT subtract from this +2.
SECURITY-STATE LIFETIME MISMATCH: +1
Award +1 when the patch directly establishes that security-relevant state such as:
* dumpability;
* credentials;
* ownership;
* capabilities;
* security labels;
* authorization mode;
* namespace/security-domain identity
ceases to be available before the protected task/object/resource ceases to be
externally accessible, causing later access checks to make a weaker decision.
Strong patch indicators include:
* caching security state before an object is detached/destroyed;
* moving authorization state to a longer-lived object;
* carrying old security state across exit/teardown;
* fixing a NULL/no-owner/no-mm special case so that authorization survives the
  lifecycle transition.
This signal is independent of the authorization-bypass +2 because:
* +2 scores the incorrect ALLOW-vs-DENY decision;
* +1 scores the concrete lifecycle mechanism that causes security policy to
  disappear prematurely.
Do not award when security state loss does not affect an actual authorization
decision.
CONCRETE REPEATED RELEASE / REFCOUNT SIGNAL
Concrete repeated release/refcount operation: +1
Apply when the patch directly establishes:
    release/drop/put(object)
        ->
    the same local/reference remains reachable
        ->
    a later deterministic path performs another release/drop/put on that
    exact same reference
AND the release operation can:
* decrement a lifetime refcount;
* invoke object destruction;
* free the object;
* release nested security-relevant state.
This signal captures that the stale operation actively MUTATES object lifetime
state rather than merely reading a dangling pointer or passing a stale pointer
into a helper that immediately faults.
Examples:
* kref_put() on the same dangling object after an earlier kref_put() may have
  reached zero;
* refcount_dec_and_test()-style lifetime operation on an exact stale object;
* second put/free/release on an exact object whose first release may have
  destroyed it;
* second object-lifetime release through an error/fail path after an earlier
  success/skip path already released the same reference.
The second operation does NOT need to establish arbitrary kernel write.
The important distinction is that the vulnerable operation itself performs a
WRITE-LIKE lifetime/refcount mutation through a reference whose object lifetime
may already have ended.
Do NOT award when:
* the second release is only hypothetical;
* the two operations use independently valid references;
* the release is harmless/idempotent;
* the first operation cannot end object lifetime;
* actual stale reuse requires an unrelated race not established by the patch;
* the helper only reads the stale object and faults;
* the only evidence is a generic commit phrase such as "possible double free"
  without enough mechanics to establish the repeated lifetime operation.
Do NOT award solely because a helper is named:
* put;
* release;
* free;
* drop.
Verify from supplied context or normal well-established helper semantics that
the operation actually affects object lifetime/refcount and can participate in
destruction/freeing.
This +1 is independent of the base Real UAF +2 because:
* Real UAF +2 scores the existence of the lifetime violation;
* this +1 scores the concrete second lifetime-mutating operation performed
  through the potentially dangling reference.
However, avoid double-counting.
Do NOT additionally award:
* Weak LPE concern +1;
* generic weak corruption +1;
* Structured stale-object exploitation leverage +1;
for the SAME second release/refcount fact.
Structured stale-object leverage may coexist only when a DISTINCT later
post-lifetime operation consumes meaningful structured fields beyond the
repeated release/refcount mutation itself.
Strong exploitation leverage +2 may replace weaker leverage interpretation when
controlled reclaim, refcount takeover, directed corruption, callback control,
or another strong primitive is independently established.
ACTIVE STRUCTURED OBJECT VS FIXED STALE STORAGE
For every UAF distinguish:
## FIXED STALE STORAGE
Examples:
* original transfer buffer;
* fixed driver context;
* fixed DMA buffer;
* fixed URB context.
Typical properties:
* same stale address;
* device/controller-generated data;
* no replacement demonstrated;
* no callback/security fields consumed;
* teardown/disconnect/suspend;
* specialized peripheral;
* crash/KASAN only.
Still receive UAF +2.
But do NOT automatically receive structured leverage or floor 5.
A fixed async stale buffer written later by hardware/controller is NOT equivalent
to a concrete repeated release/refcount operation merely because both involve
post-lifetime access.
## ACTIVE STRUCTURED OBJECT
A stale reference to a nontrivial kernel object whose fields affect:
* calculations;
* traversal;
* resource decisions;
* scheduling;
* pointers;
* lengths;
* offsets;
* indices;
* ownership;
* object selection;
* lifetime/refcount state;
* other active behavior.
Keep base UAF +2.
But IMPORTANT:
Object complexity alone is NOT exploitation leverage.
Examples of complex objects that may still be crash-only:
* struct bpf_prog;
* struct net_device;
* struct file;
* struct socket;
* qdisc/scheduler objects;
* filesystem objects;
* driver context.
Explicitly inspect WHAT the stale path actually consumes or modifies.
A second concrete refcount/lifetime mutation on a potentially freed active object
is stronger than an ordinary stale read, even when no controlled reclaim has
yet been demonstrated.
This still does NOT automatically prove:
* arbitrary write;
* controlled reclaim;
* LPE;
* callback control;
* C/I impact.
STRUCTURED STALE-OBJECT EXPLOITATION LEVERAGE
Structured stale-object exploitation leverage: +1
Apply only when ALL or nearly all are established:
1. concrete UAF exists;
2. stale object is ACTIVE STRUCTURED OBJECT;
3. attacker materially influences object state or relevant replacement/reuse;
4. later stale use consumes fields/state in a way that remains meaningful under
   plausible object reuse/replacement and can affect:
   * memory access;
   * ownership;
   * object selection;
   * callbacks/ops;
   * resource lifetime;
   * pointer traversal;
   * offsets/lengths/indices;
   * another security-relevant operation;
5. evidence supports something meaningfully beyond immediate cleanup fault or
   ordinary stale dereference.
Do NOT award merely because:
* stale object is complex;
* cleanup passes stale pointer to destructor;
* dereferencing stale fields causes Oops/page fault;
* object type contains pointers/callbacks somewhere;
* allocator reuse is theoretically possible;
* object is BPF/security-sensitive.
A cleanup/destructor stale dereference whose demonstrated consequence is only a
kernel fault remains constrained CLASS_B unless meaningful reuse leverage is
separately established.
A concrete repeated release/refcount operation has its OWN +1 rule.
Do NOT award Structured stale-object exploitation leverage +1 merely because the
second stale operation is kref_put()/put()/release().
To award both repeated-release +1 and structured-leverage +1, establish a
distinct additional stale structured operation beyond the second lifetime
mutation.
Do NOT also award Weak LPE concern for the same fact.
If controlled reclaim/object substitution is demonstrated, use Strong leverage
+2 instead.
UAF EXPLOITATION-LEVERAGE ANALYSIS
After base UAF +2, ask whether Important-grade leverage exists.
Strong indicators include:
1. attacker controls replacement/reclaimed contents;
2. attacker can cause useful alternate object to occupy stale address;
3. stale use consumes callbacks/ops/function pointers;
4. stale use consumes pointers/offsets/descriptors/credentials/ownership/refcount
   state in a way useful after plausible reuse;
5. attacker controls post-free write contents/destination;
6. repeatable unprivileged trigger gives meaningful reuse/placement control;
7. stale object crosses layer/API boundary and reused memory is accepted as valid
   structured object;
8. exploit chain yields LPE/arbitrary R/W/policy bypass.
Also distinguish a concrete repeated lifetime mutation from an ordinary stale
read:
    first release may end lifetime
        ->
    exact dangling reference survives
        ->
    second release/refcount mutation occurs
This does NOT automatically establish Strong exploitation leverage +2.
However, it is materially stronger than a shallow cleanup stale dereference and
may justify:
* Concrete repeated release/refcount +1;
* REAL UAF FLOOR 5;
* ImportantCandidate=YES;
* ManualReview=REQUIRED;
* AutoDowngradeAllowed=NO;
when the complete object lifetime and second mutation are concrete and
post-lifetime exploitation leverage remains materially unresolved.
Generic theoretical possibility of heap reuse is NOT enough for Strong +2.
REPEATED RELEASE / REFCOUNT PARANOID LEVERAGE CALIBRATION
A concrete repeated release/refcount UAF may support an additional paranoid +1
ONLY when the patch-supported mechanics establish more than:
"double release might theoretically be exploitable."
The additional paranoid +1 may be awarded when:
1. the first release can actually end object lifetime;
2. the same exact stale reference survives;
3. the second operation performs a real write-like refcount/lifetime mutation
   through that reference;
4. object storage may therefore already be outside its original lifetime when
   the second mutation occurs;
5. the resulting mutation is not limited to a guaranteed immediate fault before
   any lifetime/refcount state can be modified;
6. this creates a technically defensible unresolved post-free corruption
   mechanism even though controlled reclaim/replacement is not yet demonstrated.
Conceptually:
    first put/release
        ->
    possible destruction/free
        ->
    stale reference survives
        ->
    second kref_put/refcount mutation
        ->
    lifetime metadata at the stale address is actively modified
This may justify paranoid +1 for unresolved post-free lifetime/refcount
corruption.
IMPORTANT:
This is NOT:
    heap reuse is theoretically possible -> +1
The scored fact is:
    the vulnerable stale operation itself performs a concrete lifetime/refcount
    mutation through storage whose original object lifetime may already have
    ended.
Do NOT award this paranoid +1 when:
* the second helper merely reads stale state and faults;
* the first release cannot free/end lifetime;
* second release is speculative;
* release is idempotent;
* only a generic UAF class is known;
* no actual lifetime/refcount mutation occurs;
* a guaranteed immediate failure prevents the mutation from reaching stale
  lifetime state.
Do NOT stack this paranoid +1 with:
* Weak LPE +1;
* Structured stale-object leverage +1;
when they describe the exact same second refcount mutation.
If controlled reclaim/refcount takeover/directed corruption is established, use
the stronger appropriate primitive instead.
KVM / GUEST-TO-HOST UAF CALIBRATION
A UAF in host KVM state is security-boundary relevant, but the mere combination:
    guest-influenced state
    +
    host-kernel UAF
    +
    virtualization boundary
does NOT by itself establish Strong guest-to-host exploitation leverage +2.
Do NOT award +2 Strong LPE plausibility / strong exploitation leverage solely
because:
* the stale object belongs to KVM host-kernel MMU or virtualization state;
* guest page-table activity participates in creating the invalid state;
* guest-controlled memory accesses participate in triggering the bug;
* the eventual stale dereference occurs in the host kernel;
* the host kernel may crash while processing guest-related state;
* successful exploitation would theoretically cross the guest/host boundary.
These facts establish that the bug affects a security-sensitive boundary and
deserve careful review, but they do not establish a strong exploitation
primitive by themselves.
Require an independently established exploitation primitive for +2, such as:
* guest-controlled or meaningfully guest-influenced reclaim/replacement;
* stale use of attacker-shaped replacement-object fields;
* guest-directed host kernel read/write;
* callback/ops/function-pointer influence;
* host ownership/refcount/credential manipulation;
* attacker-controlled post-free contents;
* demonstrated guest-to-host memory corruption beyond an ordinary stale
  dereference;
* controlled host object/type confusion;
* another concrete mechanism that remains security-useful after excluding the
  crash itself.
A stale host KVM pointer that later causes an ordinary rmap/MMU/list/object walk
and faults is still a real CLASS_B UAF, but is not automatically a +2
guest-to-host exploitation primitive.
For a KVM UAF with:
* demonstrated host crash / DoS;
* no controlled reclaim;
* no attacker-shaped replacement contents;
* no arbitrary/directed host kernel read/write;
* no callback/function-pointer control;
* no demonstrated guest-to-host privilege or isolation bypass;
normally score the established UAF, crash, reachability, and execution-mode
requirements independently.
Manual review may still be REQUIRED or RECOMMENDED because the corruption is in
host KVM state.
However:
ManualReview=REQUIRED
is NOT itself evidence for +2 Strong exploitation leverage.
Likewise:
ImportantCandidate=YES
must not be used as circular justification for +2.
First establish the primitive, then derive ImportantCandidate and ManualReview
from that primitive.
If the only argument for +2 is:
"this is a host-kernel UAF reachable from guest-influenced KVM state"
do NOT award the +2.
KVM ATTACKER-ROLE RULE
For KVM vulnerabilities, explicitly distinguish the security principal that can
perform each stage of the trigger.
At minimum distinguish:
A. malicious guest code;
B. local host userspace/VMM process with /dev/kvm access;
C. host virtualization administrator / host root.
Do NOT merge the capabilities of these actors into one attacker unless evidence
shows that one security principal can perform the COMPLETE required trigger
sequence.
Guest control over:
* guest page tables;
* guest memory contents;
* guest virtual/physical accesses;
* guest CPU state
does NOT automatically mean the guest can perform host userspace operations such
as:
* deleting or replacing KVM memslots;
* KVM_SET_USER_MEMORY_REGION changes;
* changing host-side mappings;
* host MADV_DONTNEED;
* host MMU-notifier-triggering operations;
* enabling dirty logging;
* changing host KVM VM configuration;
* creating/destroying host memory backing;
* other VMM-controlled lifecycle operations.
Likewise, a VMM process with /dev/kvm access is not automatically equivalent to
malicious guest code.
When the complete trigger requires:
guest-controlled action
+
host-VMM-controlled lifecycle operation
record it as a COMPOUND TRIGGER unless supplied evidence shows the guest can
cause the VMM operation through an attacker-accessible interface.
For compound triggers:
* do not award Local unprivileged trigger solely from guest influence;
* do not award Attacker-influenced lifetime manipulation solely because the
  guest controls one stage;
* do not award guest-to-host exploitation leverage by combining guest control
  with VMM control;
* identify which principal controls object free/zap/replacement;
* identify which principal controls the later stale-object traversal.
Attacker-influenced active-object state / repeatable lifetime manipulation +1
requires that the same attacker/security principal can materially drive the
relevant vulnerable lifetime sequence, or that an independently established
interface lets one attacker reliably induce the other stages.
For example:
guest page-table modification
+
host-controlled memslot deletion
+
host-controlled dirty-log or MMU notifier operation
does NOT automatically qualify for +1 repeatable lifetime manipulation by the
guest.
A local VMM process with /dev/kvm access may have broader control and may qualify,
but score that as a local VMM attacker model, not as a pure guest-to-host model.
In Reachability analysis, explicitly state whether the evaluated attacker is:
* guest-only;
* VMM/local-host user;
* host administrator;
* unresolved/compound.
Do not use the strongest abilities from several attacker roles simultaneously
unless the complete attack model actually permits it.
CONSTRAINED UAF / ASYNC / CLEANUP STALE-OBJECT CASE
Do NOT treat every UAF as Important-preserving.
A UAF may remain constrained when evidence mainly shows:
* fixed async DMA/USB/IO stale buffer/context;
* same stale address;
* device-generated contents;
* no replacement/reclaim;
* no sensitive callbacks/credentials/pointer fields consumed;
* teardown/disconnect/suspend;
* specialized peripheral.
A STRUCTURED UAF may ALSO remain constrained when:
* stale use occurs primarily in cleanup/destructor/unregister/release/
  namespace-exit processing;
* demonstrated result is immediate page fault/Oops/crash;
* no controlled reclaim/replacement;
* no attacker-controlled post-free contents;
* no callback/ops path from reclaimed data;
* no arbitrary/directed read/write;
* no disclosure;
* no security-boundary bypass;
* no concrete repeated lifetime/refcount mutation on the same dangling object.
Such cases still receive UAF +2 but do NOT automatically receive:
* Structured stale-object leverage;
* Weak LPE;
* Strong LPE;
* Floor 5;
* ImportantCandidate=YES.
IMPORTANT:
The word "cleanup", "fail", "error", "destructor", or "release" does NOT by
itself make a UAF constrained.
Inspect what the stale operation actually DOES.
IMPORTANT DOUBLE-RELEASE / REPEATED-LIFETIME EXCEPTION
Do NOT classify a UAF as constrained merely because the second stale use occurs
in an:
* error path;
* fail label;
* cleanup path;
* destructor path;
* unregister path;
* release path;
when ALL or nearly all of the following are established:
1. an earlier release/drop/put can end the object's lifetime;
2. the exact same local/reference remains reachable after that release;
3. the reference may therefore become dangling;
4. a later path performs another lifetime-mutating:
   * put;
   * release;
   * free;
   * refcount decrement;
   * kref_put;
   * equivalent object-lifetime operation
   on that same reference;
5. the second operation is concrete from the patch/control flow rather than a
   generic theoretical consequence.
Distinguish:
A. ORDINARY CLEANUP STALE DEREFERENCE
    stale pointer
        ->
    cleanup/destructor helper
        ->
    stale field read / immediate fault / Oops
This may remain constrained CLASS_B.
from:
B. CONCRETE REPEATED LIFETIME CORRUPTION
    release(ref)
        ->
    object lifetime may end
        ->
    same dangling ref survives
        ->
    later release/put/refcount/free(ref)
        ->
    second lifetime mutation through potentially freed storage
This is materially stronger than an ordinary cleanup stale dereference.
Do NOT require:
* controlled reclaim;
* arbitrary kernel R/W;
* callback hijack;
* demonstrated LPE;
merely to recognize category B as stronger Class B.
When category B is established, it may justify:
PrimitiveClass=CLASS_B
ImportantCandidate=YES
ManualReview=REQUIRED
AutoDowngradeAllowed=NO
even when controlled reclaim, arbitrary R/W, or demonstrated LPE is not yet
available.
This does NOT automatically make the vulnerability CLASS_A or score 7+.
The intended calibration is generally:
* at least Actionable Moderate when reachability is meaningful and no strong
  reducing condition exists;
* Important-vs-Moderate manual review when post-lifetime mutation remains
  materially unresolved;
* Strong Important only when arithmetic/independent evidence supports it.
Do NOT apply this exception merely because a commit uses the phrase:
"double free"
"double release"
"use-after-free"
Verify the actual lifetime mechanics.
CONCRETE RCU REFERENCED-OBJECT LIFETIME MISMATCH
Concrete RCU referenced-object lifetime mismatch: +1
Award +1 when ALL or nearly all are established:
1. object/container A remains legitimately visible to concurrent RCU readers;
2. A contains or exposes a reference to another lifetime-managed object B;
3. readers may obtain or continue using B through A while A remains within its
   valid RCU-visible lifetime;
4. the vulnerable writer/destroy path performs put/release/free or another
   lifetime-ending operation on B BEFORE the RCU grace period protecting A has
   completed;
5. the fix moves that put/release/free into or after the RCU callback/grace
   period, or otherwise extends B's lifetime to cover all legitimate readers;
6. the commit or surrounding code explicitly establishes that concurrent readers
   may still observe/use A->B.
This is an independent synchronization/lifetime signal beyond the base Real UAF
+2 because:
* Real UAF +2 scores existence of post-lifetime use;
* this +1 scores the concrete broken cross-object RCU lifetime invariant that
  makes the stale use possible during otherwise legitimate reader execution.
Do NOT award merely because:
* RCU appears somewhere in the code;
* call_rcu() is used;
* an object is freed during teardown;
* theoretical readers might exist;
* the fix simply delays cleanup without evidence that readers require the
  referenced object to remain alive.
Do NOT infer controlled reclaim, arbitrary R/W, confidentiality, integrity, or
LPE from this signal.
When this signal applies to an ACTIVE STRUCTURED OBJECT and host-admin-equivalent
privilege is not positively established, conservative ActionableScore should
normally not remain below 5.
When the stale referenced object participates in nontrivial active kernel
processing and the exact post-lifetime reader behavior remains unresolved,
paranoid ActionableScore may reasonably be one point higher, typically 6,
without requiring controlled reclaim.
NARROW TEARDOWN / PERCPU LIFETIME CALIBRATION
RCU/percpu/teardown bugs must be classified from actual stale use.
Tend toward Class C or constrained Class B when:
* stale pointer tied to fixed/percpu object;
* attacker does not materially influence replacement;
* stale use is shallow and crashes;
* one-time teardown transition;
* meaningful reclaim unavailable;
* no concrete second lifetime/refcount mutation exists.
Same calibration may apply to structured cleanup UAF if stale use is limited to
destructor/unregister and only demonstrated result is crash.
However, do NOT apply this calibration to a concrete repeated release/refcount
case merely because both lifetime operations happen during error/cleanup paths.
Do NOT apply merely because bug uses RCU/concurrency.
Do NOT suppress an active structured UAF with:
* attacker-influenced replacement;
* repeated object generation;
* repeatable lifetime transitions;
* nontrivial stale processing;
* meaningful post-reuse field consumption;
* concrete repeated lifetime/refcount mutation.
CRASH CORRUPTION VS NON-CRASH EXPLOITATION
Concrete:
* double list_del;
* poison dereference;
* invalid list operation;
* BUG;
* invalid stale dereference;
* stale cleanup pointer causing page fault
may support crash/DoS.
Do NOT count same evidence again as independent strong non-crash primitive.
Ask:
"What useful attacker-controlled primitive remains after excluding the crash?"
Possible strong answers:
* attacker-controlled write;
* controlled reclaim;
* active object replacement;
* controlled list/object contents;
* semantic reinterpretation;
* disclosure;
* credential/boundary compromise.
For repeated-release/refcount bugs, also ask:
"After excluding the crash, does the vulnerable operation itself still perform a
lifetime/refcount mutation through storage whose original object lifetime may
already have ended?"
If YES, that fact is stronger than crash-only stale dereference and may support
the dedicated repeated-release +1 and unresolved Class B preservation.
It still does NOT automatically establish arbitrary write, controlled reclaim,
or Strong LPE +2.
REAL UAF SCORE FLOOR
Apply floors AFTER raw arithmetic and genuine penalties.
## FLOOR 4
If:
* RealUAF=YES;
* stale reference actually used;
* bug is not clearly fixed stale storage with immediate crash-only behavior;
* host-admin-equivalent privilege is NOT positively established;
then conservative score normally should not be below 4.
This is calibration, not Important-grade proof.
## FLOOR 5
Apply only when FLOOR 4 conditions hold AND meaningful exploitation surface
beyond ordinary cleanup/fault behavior is established through at least one of:
* attacker materially influences security-relevant stale object state consumed
  after reuse;
* attacker creates/replaces object in a way giving meaningful reuse leverage;
* attacker repeatedly drives lifetime transition and stale use performs
  nontrivial active processing beyond cleanup failure;
* vulnerable API is positively established below host admin AND stale-object
  exploitation surface is meaningful;
* stale use continues into security-relevant structured processing;
* attacker influences stale replacement contents/post-free state;
* stale use performs a concrete second release/put/refcount/free operation on
  the exact same reference after an earlier release may have ended the object's
  lifetime.
For the repeated-release/refcount FLOOR 5 condition, require that:
* the first release can actually affect lifetime/refcount and may destroy/free
  the object;
* the same exact reference survives;
* the second operation concretely mutates lifetime/refcount state;
* the second operation is not harmless/idempotent;
* the condition is established from patch/control flow/helper semantics, not
  merely from the words "double release".
Controlled reclaim is NOT required merely to apply this specific FLOOR 5
condition.
Then conservative score MUST NOT be below 5 UNLESS a concrete strong reducing
condition applies.
Possible reducing conditions:
* proven host-admin-equivalent privilege;
* physical-only/rare hardware;
* genuinely hard one-shot race;
* fixed async stale buffer;
* privilege-gated cleanup UAF covered by exception below.
IMPORTANT:
A concrete repeated release/refcount operation is generally NOT equivalent to
the fixed async stale-buffer exception because the second operation itself
actively mutates object lifetime/refcount state.
The floor is NOT intended to force every complex-object UAF to 5.
BPF / PRIVILEGED CONTROL-PLANE EXCEPTION TO UAF FLOOR 5
Do NOT apply REAL UAF FLOOR 5 merely because the stale object is an ACTIVE
STRUCTURED OBJECT when ALL or nearly all of the following are true:
* triggering requires a privilege-gated kernel control-plane API such as
  BPF/eBPF/XDP loading or attachment;
* ordinary unprivileged reachability in the evaluated product is not established;
* the demonstrated stale use occurs primarily in cleanup, teardown, unregister,
  destroy, release, or namespace-exit processing;
* demonstrated impact is a kernel fault / crash / DoS;
* controlled reclaim or attacker-controlled object replacement is not shown;
* attacker-controlled post-free contents are not shown;
* callback/function-pointer dispatch from reclaimed contents is not shown;
* arbitrary or directed kernel read/write is not shown;
* no security-boundary bypass or LPE is demonstrated;
* no concrete repeated release/refcount mutation on the exact dangling object is
  established.
In this case:
* do not force Conservative ActionableScore to 5;
* allow conservative score 3-4 when ordinary arithmetic supports it;
* CLASS_B may still be used;
* manual review may still be recommended;
* ImportantCandidate does not automatically become YES;
* AutoDowngradeAllowed may be YES when crash-only behavior is stable and no
  meaningful unresolved exploitation primitive remains.
The mere fact that the stale object is structurally complex, such as:
* struct bpf_prog;
* struct net_device;
* another rich kernel object
is not enough for FLOOR 5.
Passing stale object into another helper/destructor is also not enough.
However, if the stale helper itself performs a concrete second lifetime/refcount
mutation after an earlier release may have ended lifetime, evaluate the
CONCRETE REPEATED RELEASE / REFCOUNT SIGNAL and the DOUBLE-RELEASE exception
rather than mechanically treating the case as cleanup-only.
If later evidence establishes:
* controlled reclaim;
* active replacement;
* callback/ops consumption after reuse;
* attacker-controlled post-free contents;
* arbitrary/directed read/write;
* security-boundary bypass;
* LPE;
then this exception no longer suppresses stronger scoring.
RACE / TIMING RULE
Hard or unreliable race / special timing required: -1
Do NOT subtract merely because vulnerability is a race.
Do NOT equate:
race == AC:H == -1
Apply -1 only when evidence establishes materially:
* narrow;
* low-probability;
* externally uncontrollable;
* difficult-to-repeat
timing.
May justify -1:
* one-shot teardown race;
* narrow hardware timing;
* exact async ordering attacker cannot repeatedly drive;
* rare interrupt/completion interleaving.
Do NOT subtract when:
* attacker repeatedly triggers both operations;
* race naturally occurs under load;
* attacker controls create/destroy/update loops;
* repeated attempts are cheap;
* patch merely says race;
* bug is an ordered error-path sequence rather than a timing race.
A required sequence such as:
    operation A
        ->
    later error B
        ->
    fail path C
is NOT automatically a hard race.
Do not apply -1 merely because several state conditions are required.
HOST ADMIN UNKNOWN VS NO RULE
HostAdminRequired=NO requires POSITIVE evidence that the COMPLETE vulnerable
operation is reachable below-host-admin-equivalent privilege.
Absence of evidence proving host-admin privilege is NOT sufficient for NO.
Use:
HostAdminRequired=YES
when host-admin-equivalent privilege is positively established.
HostAdminRequired=NO
when below-host-admin reachability is positively established.
HostAdminRequired=UNKNOWN
when supplied evidence does not resolve the complete privilege boundary.
For DRM/KMS/display-control paths:
Do NOT infer HostAdminRequired=NO merely because a local desktop user exists.
HostAdminRequired=NO is appropriate when supplied call-path/product context or
well-established exact interface semantics establishes that the complete
vulnerable KMS/display operation is reachable by a below-host-admin actor such
as an appropriately authorized DRM master/compositor/display service/seat
context.
Otherwise use UNKNOWN.
For privilege-gated BPF/eBPF/XDP paths, prefer UNKNOWN over NO unless supplied
analysis establishes that the complete:
* load;
* JIT;
* attach;
* device-bound setup;
* trigger;
* cleanup
sequence works below host-admin-equivalent privilege in the evaluated product.
Do not infer NO merely from:
* capability can theoretically be delegated;
* container root exists;
* reproducer uses netns;
* veth is namespace aware.
CAP_NET_ADMIN NAMESPACE RESOLUTION RULE
Whenever CAP_NET_ADMIN is relevant, determine WHICH namespace governs the exact
security-relevant check.
Distinguish:
A. host/init_user_ns CAP_NET_ADMIN;
B. ns_capable(target_user_ns, CAP_NET_ADMIN);
C. netlink_ns_capable/netlink_net_capable against net->user_ns;
D. capability over separately owned target netns;
E. namespace-aware API still requiring host-owned physical/device state.
For qdisc/rtnetlink:
Do NOT assume host CAP_NET_ADMIN merely because tc requires CAP_NET_ADMIN.
But a namespace-scoped network capability for ONE stage does NOT prove the
COMPLETE trigger chain is namespace-scoped.
NAMESPACE-SCOPED PRIVILEGE EVIDENCE RULE
Presence of:
* netns;
* veth;
* container;
* namespace-local device;
* namespace cleanup
does NOT itself establish NamespaceScopedPrivilege=YES.
Set YES only when:
1. relevant capability checks are namespace-scoped; AND
2. ALL required privilege-gated stages can be completed below host admin.
For BPF/XDP separately evaluate:
* program loading privilege;
* JIT availability;
* constant blinding/hardening configuration;
* device-bound program creation;
* XDP attachment;
* netdevice control;
* namespace creation;
* namespace cleanup.
If only netdevice management is namespace-scoped but BPF load/attach remains host
privileged:
do NOT classify complete trigger as namespace-scoped unprivileged.
Use UNKNOWN when unresolved.
If exact namespace reachability is unresolved:
* penalty is at most -1 rather than -2;
* but do NOT award Local unprivileged +1.
PRIVILEGE PENALTY REFINEMENT
1. FULL HOST-ADMIN-EQUIVALENT: -2
Use only when exploitation actually requires:
* host root;
* init_user_ns CAP_SYS_ADMIN;
* host CAP_NET_ADMIN over host-owned resources;
* equivalent broad host control;
AND no additional meaningful boundary is bypassed.
2. REDUCED / DELEGATED PRIVILEGE: -1
Use when reduced capability/management right is positively established below host
root.
Examples:
* constrained container root;
* service account with CAP_NET_ADMIN;
* delegated network-management process.
Do NOT choose merely because delegation is theoretically possible.
3. ATTACKER-OBTAINABLE NAMESPACED CAPABILITY: 0
Use only when ordinary attacker can positively be shown to:
* create namespace;
* obtain capability there;
* instantiate object;
* perform all required privilege-gated operations;
* exercise vulnerable path.
4. ORDINARY UNPRIVILEGED: 0
Also award Local unprivileged +1 when established.
PRIOR PRIVILEGED SETUP RULE
requires_prior_privileged_setup=true
ONLY when separate host-privileged actor must:
* provision;
* attach;
* enable;
* delegate;
* move;
* expose;
* configure
attack path.
Do NOT infer merely from:
* CAP_NET_ADMIN somewhere;
* namespace existence;
* optional subsystem;
* runtime object configuration;
* kernel CONFIG option.
But root-controlled:
* sysctl;
* boot parameter;
* BPF policy;
* device assignment;
* prior host-created object
may be genuine prerequisites when attacker cannot establish them.
SUBSYSTEM / CONFIGURATION EXPOSURE RULE
Rare AND difficult-to-reach subsystem/configuration: -1
Use only when BOTH:
* genuinely unusual; AND
* attacker cannot ordinarily instantiate/reach it.
Do NOT subtract merely because subsystem is:
* specialized;
* niche;
* optional;
* not active at boot.
May justify:
* unusual boot option;
* experimental filesystem feature;
* special hardware;
* deprecated mode;
* host-created topology;
* privileged sysctl attacker cannot change.
Normally NOT enough:
* attacker-created qdisc;
* netlink object;
* namespace;
* runtime object attacker may instantiate;
* AF_ALG;
* io_uring;
* ordinary FS operation;
* netfilter/XFRM when attacker already has required control.
LEGACY / HARDWARE PENALTIES
Legacy/non-default execution mode: -1
Examples:
* shadow paging;
* software MMU fallback;
* deprecated virtualization mode.
Physical-only or rare hardware-only: -2
Use only when uncommon physical hardware/access is materially required.
Do not apply merely because code is a driver.
Common consumer/workstation/server GPU hardware is hardware-specific but is not
automatically "rare hardware".
DEVICE QUIRK / FREEZE CALIBRATION
Hardware compatibility quirk, device-local hang, initialization failure, or
device-local freeze is normally Low/ordinary Moderate when:
* no memory corruption;
* no security boundary;
* effect limited to device;
* attacker influence weak/privileged.
Do not escalate merely because failure occurs in kernel driver.
Do not treat device reset/freeze as host-wide strong DoS unless host-wide impact
is supported.
Remote/unprivileged device input, host-wide failure, DMA corruption, page
ownership corruption, concrete UAF/double release, or another concrete primitive
may justify higher score.
A driver double release/refcount UAF must be scored under the lifetime rules,
not reduced to a generic "device-local driver failure" merely because the code
belongs to a GPU/display/audio/device driver.
DENIAL OF SERVICE / AVAILABILITY
Reliable kernel crash / strong DoS: +1
CVSS A:H/A:L is NOT evidence for this point. Ignore the CVSS Availability metric
when deciding whether to award it.
Apply when realistic:
* kernel crash;
* panic;
* host-wide fatal fault;
* filesystem shutdown
is supported.
For a concrete double-release/refcount bug, a realistic kernel fault caused by
post-lifetime refcount/free processing may support this +1.
Do not require an observed panic when the lifetime mechanics directly support a
kernel fault, but distinguish plausible crash from guaranteed panic.
Availability impact realistic: +1
Do NOT add automatically when crash/DoS +1 is already counted.
Second Availability point requires a DISTINCT effect beyond immediate crash.
STRICT CRASH / AVAILABILITY DOUBLE-COUNT RULE
If +1 Reliable kernel crash / strong DoS is awarded, then the same:
* Oops;
* page fault;
* panic;
* host crash;
* fatal stale-pointer fault;
* double-release-induced kernel fault
MUST contribute exactly ZERO additional Availability points unless a distinct
consequence exists.
Reliability of the same crash is NOT distinct.
Repeatability of same crash is NOT distinct.
Do NOT add paranoid +1 merely because:
* crash is reliable;
* crash occurs during namespace cleanup;
* same setup reproduces it;
* host goes down.
Additional Availability +1 requires something beyond the immediate crash, such
as:
* persistent filesystem shutdown;
* persistent data loss;
* unrecoverable resource exhaustion;
* lasting unavailability beyond ordinary recovery;
* another independently demonstrated availability mechanism.
WARN_ON continuation:
WARN_ON alone is +0 unless evidence supports actual fatal consequence.
RESOURCE EXHAUSTION RULE
Pure resource exhaustion normally Low/ordinary Moderate unless unusually broad,
persistent, or cross-boundary.
Do not treat:
* allocation failure;
* queue exhaustion;
* memory pressure;
* descriptor exhaustion;
* resource leakage;
* accounting growth;
* workqueue backlog;
* transient starvation
as Important merely because kernel resources are affected.
Escalate when:
* memcg/cgroup limits bypassed;
* cross-container consumption;
* namespace accounting bypass;
* host-wide exhaustion from constrained workload;
* persistent leak survives cleanup;
* isolation mechanism defeated.
Avoid double-counting exhaustion and same boundary-bypass consequence.
This rule limits escalation from the CONSEQUENCE of resource exhaustion.
It does not suppress the independent +1 Concrete persistent kernel
resource/reference leak signal when an actual missing release/put is directly
established.
CONCRETE RESOURCE / REFERENCE LEAK SIGNAL
Concrete persistent kernel resource/reference leak: +1
Apply when the patch directly establishes that a kernel resource or lifetime
reference is acquired and then permanently lost from normal cleanup, for example:
* missing put/release after get;
* folio/page reference removed from a batch before batch cleanup;
* leaked skb/object/device/file reference;
* mapping/DMA/resource reference that cannot be recovered by the normal cleanup
  path.
Award only when the leak is concrete, not merely a theoretical consequence of
an error path.
This +1 represents the established lifetime/resource-management defect itself.
It does NOT mean strong DoS or Important-grade impact.
Do NOT additionally award generic resource-exhaustion points unless evidence
shows meaningful accumulation, persistent host-wide pressure, isolation bypass,
or another independently established consequence.
A concrete repeatable reference leak reachable through ordinary runtime activity
may therefore score above an otherwise harmless bookkeeping bug even when a
reliable crash or host-wide exhaustion has not yet been demonstrated.
Do NOT confuse:
missing release -> persistent reference leak
with:
release -> dangling reference survives -> second release/refcount mutation.
The latter belongs to CONCRETE REPEATED RELEASE / REFCOUNT SIGNAL.
CONFIDENTIALITY / INTEGRITY IMPACT
Confidentiality plausible: +1
CVSS C:H/C:L is NOT evidence for this point. Ignore the CVSS Confidentiality
metric when deciding whether to award it.
Require:
* read-back;
* disclosure;
* protected-object read;
* sensitive FD/resource access;
* demonstrated confidentiality consequence.
Do not award because UAF theoretically could leak.
Integrity plausible: +1
CVSS I:H/I:L is NOT evidence for this point. Ignore the CVSS Integrity metric
when deciding whether to award it.
Require unauthorized modification of:
* protected kernel state;
* another principals data;
* privileged file-backed data;
* shared pages;
* credentials;
* policy;
* important FS metadata;
* sensitive object state.
Do not award merely because bookkeeping is wrong.
Do not award C/I merely because reclaimed memory theoretically could contain
sensitive data.
A second refcount mutation on potentially freed memory is a concrete lifetime
corruption fact, but it does NOT by itself establish CVSS-like C:H or I:H.
Score the lifetime primitive separately.
FILESYSTEM / STORAGE SIGNALS
Filesystem/storage metadata corruption reachable by unprivileged local user: +1
Important filesystem/storage path: +1
Examples:
* XFS/ext4/btrfs mapping integrity;
* journal/recovery;
* writeback;
* page cache;
* block layer;
* extent/refcount ownership.
Filesystem shutdown/assertion without broader corruption usually Moderate.
DIRTY-PIPE-LIKE / OWNERSHIP / COW RULES
Dirty-Pipe-like primitive: +1
Use for meaningful shared-page/file-backed corruption weaker than full ownership
violation.
Dirty-Pipe-like ownership/COW violation: +2
Use INSTEAD OF +1 when attacker-authorized write to A modifies externally owned
or independently permissioned B through shared physical storage/COW failure.
Require support for chain:
attacker writes A
->
A shares storage with B
->
COW/shared-state logic fails
->
write reaches shared storage
->
B changes
->
attacker lacks permission to B
Do NOT require commit to literally say permission bypass if semantics prove it.
Do NOT award merely from stale mapping/reflink state/generic FS corruption.
When supported, independent signals may include:
* ownership/COW +2;
* Integrity +1;
* Local unprivileged +1;
* FS metadata corruption +1;
* Important FS path +1;
* Practical exploit chain +1.
Do NOT stack same shared-block primitive as multiple separate +2 categories.
Page-cache / privileged file-backed corruption: +2
Do not stack with COW +2 for same primitive.
SECURITY-BOUNDARY / AUTHORIZATION SIGNALS
CONCRETE AUTHORIZATION DECISION BYPASS: +2
Award +2 when the patch directly establishes that a kernel access-control
decision can incorrectly change from:
    DENY / requires capability / requires security condition
to:
    ALLOW
because required authorization state is skipped, lost, bypassed, or evaluated
incorrectly.
Examples include:
* capability check skipped when a state pointer becomes NULL;
* dumpability restriction disappears during task lifecycle transition;
* credential/ownership check bypassed for a special state;
* LSM/capability gate omitted on one reachable branch;
* namespace/security-domain lookup uses an incorrectly weaker authority.
Requirements:
1. a real access-control gate is identified;
2. the vulnerable path concretely bypasses or weakens that gate;
3. the fixed code restores the missing authorization condition;
4. successful authorization has externally meaningful kernel behavior.
This signal does NOT require:
* kernel memory corruption;
* arbitrary read/write;
* demonstrated LPE;
* a specific stolen FD;
* a complete downstream exploit chain.
Do not award merely because code contains capable(), ptrace, credentials, or
security terminology. The ALLOW-vs-DENY change must be concrete.
Security-boundary bypass with practical sensitive-object access: +2
Examples:
* ptrace bypass;
* pidfd_getfd privileged FD access;
* namespace/container escape;
* capability boundary bypass;
* credential/dumpability bypass;
* LSM/SELinux/seccomp bypass;
* permission bypass.
Sensitive file / credential / FD theft: +2
Examples:
* /etc/shadow;
* SSH keys;
* service secrets;
* privileged sockets;
* credentials;
* root-owned descriptors.
Cross-boundary isolation/policy bypass: +1
Examples:
* memcg/cgroup;
* namespace resource isolation;
* container-to-host interference.
Do not stack +1 and +2 for same exact boundary.
IMPORTANT:
A helper-level authorization bypass and a downstream protected-resource
consequence may be independent signals when the supplied evidence establishes
both:
1. a real authorization check is bypassed; AND
2. the bypass gives access to a distinct privileged FD/file/resource that the
   attacker is not normally allowed to obtain or inspect.
Do not collapse a demonstrated privileged-resource theft chain into a generic
"information exposure" label.
PROCESS EXIT / PTRACE / PIDFD RULES
Process-exit privileged resource lifetime window: +1
Apply when privilege/dumpability/mm state changes before privileged resources are
closed and unauthorized inspection/copying becomes possible.
Consider:
* pidfd_getfd;
* procfs;
* PTRACE_MODE_READ_FSCREDS;
* PTRACE_MODE_ATTACH_REALCREDS;
* no-mm tasks;
* exiting privileged tasks;
* reduced capabilities;
* surviving privileged FDs.
A ptrace_may_access / __ptrace_may_access authorization defect is NOT necessarily
limited to low-value task-information disclosure merely because the patched
function is itself only an access-control helper.
Inspect supplied callers and advisory/exploit evidence for what SUCCESSFUL
authorization enables.
In particular consider whether bypassing ptrace_may_access can enable:
* pidfd_getfd() access to another process file descriptor;
* procfs access to protected process state;
* process_vm_* access;
* ptrace attach/read operations;
* acquisition of a privileged socket;
* acquisition of a privileged file descriptor;
* access to an already-open protected file;
* access to credential-bearing or secret-bearing resources;
* another privileged process resource.
If supplied evidence establishes:
attacker below host-admin privilege
    ->
dumpability / capability / ptrace authorization bypass
    ->
pidfd_getfd or equivalent caller succeeds
    ->
attacker obtains or accesses a privileged process FD/resource
then treat this as:
* Security-boundary bypass with practical sensitive-object access +2;
and, when the FD/resource itself is independently security-sensitive:
* Sensitive file / credential / FD theft +2.
These two signals may coexist because:
* the first scores the authorization boundary that was bypassed;
* the second scores the distinct protected resource actually obtained.
Do NOT award the second +2 merely because pidfd_getfd exists or because a
privileged process may have interesting FDs.
Require supplied evidence that a protected/sensitive resource is reachable.
If supplied advisory/exploit evidence further establishes that this access can
yield:
* root privilege escalation;
* arbitrary privileged command execution;
* privileged configuration modification;
* protected credential disclosure;
then treat the complete chain as Important-grade CLASS_A.
Do NOT leave the issue at Actionable Moderate merely because:
* no kernel memory corruption exists;
* CVSS confidentiality is numerically low;
* the upstream commit discusses uid 0 or capability dropping;
* the patch itself does not name pidfd_getfd;
* the exploit consequence appears only in supplied authoritative advisory text.
The attacker model must follow the COMPLETE supplied exploit path.
For example, if the commit discusses uid 0 kernel-thread inspection but supplied
authoritative evidence demonstrates that an ordinary local user can exploit the
same ptrace/dumpability flaw against an exiting privileged userspace process,
score the ordinary-user exploit path.
Do NOT anchor the attacker model to the narrowest example in the commit.
Conversely, do NOT infer privileged FD theft, root escalation, or arbitrary
process access from ptrace_may_access alone.
Without downstream protected-resource or exploit evidence, a ptrace/dumpability
bypass may remain Actionable Moderate/manual review.
CENTRAL AUTHORIZATION HELPER FAN-OUT: +1 paranoid,
or conservative when callers are visible
Award +1 when:
1. the patched function is a central authorization predicate/helper;
2. commit/context explicitly establishes that it guards multiple operations or
   resources beyond the object whose state caused the bug;
3. the authorization bypass occurs before downstream security hooks/callers;
4. successful return is therefore security-relevant beyond a single diagnostic
   value.
Examples:
    ptrace_may_access()
    inode_permission()
    capable()/ns_capable()-wrapped policy helper
    LSM access predicate
    credential/resource-access helper
Do not award merely because a helper has many theoretical callers.
Require either visible callers or explicit commit/context evidence that the
helper is used for multiple access-control purposes.
MEMORY LAYOUT INVARIANT RULE
Memory layout invariant restoration: +1
Apply when patch restores consistency among interdependent:
* allocation size;
* copy size;
* offsets;
* frag lengths;
* SG lengths;
* ring indices;
* actual buffer sizes.
Do not add if it duplicates an already established OOB primitive unless invariant
adds independent exploitation relevance.
STRONG SEMANTIC REINTERPRETATION SIGNAL
Strong attacker-influenced semantic reinterpretation: +2
Apply when ALL/nearly all:
1. attacker-influenced input/representation validated under semantic structure A;
2. same attacker-influenced bytes later consumed under DIFFERENT semantics due to
   vulnerability;
3. reinterpreted data represent active operations/resources/pointers/ownership/
   descriptors/control information;
4. mismatch is directly established and needs no unrelated bug.
Strong primitive even without:
* arbitrary write;
* controlled UAF;
* LPE;
* public exploit;
* panic.
Paranoid +1 only when reinterpretation plausibly affects:
* object lifetime;
* resource ownership;
* memory access;
* active execution;
* traversal/free/deref.
Do NOT award for passive metadata/wrong ordinary values/harmless disagreement.
DIRTY FRAG EQUIVALENCE
RxRPC/ESP/XFRM and similar in-place decrypt/write into externally owned skb paged
fragments should be scored primarily by shared-page/COW/ownership primitive.
Protocol rarity must not erase demonstrated ownership violation.
NETWORKING RULES
Common networking core path / packet-processing path: +1
Examples:
* TCP/IP lookup;
* common receive;
* netfilter;
* socket lookup;
* common skb processing;
* routing.
Do not award merely because source is under net/.
Local-only netlink/ioctl control-plane requiring proven host-equivalent

* strong corruption;
* meaningful namespace delegation;
* Important-grade UAF;
* authorization bypass.
TAPRIO / QDISC / RUNTIME-CONFIGURATION RULE
For qdisc/runtime-configurable networking objects:
Do NOT call configuration rare merely because qdisc not attached by default when
attacker with evaluated permission can instantiate it.
If UAF occurs because:
* RCU schedule/object replaced/freed;
* reader lacks RCU protection;
* stale structured object consumed;
classify concrete UAF first.
Then determine:
* host CAP_NET_ADMIN actually required?
* namespaced capability sufficient?
* attacker can create qdisc/device?
* attacker repeatedly replaces schedule/object?
* race repeatable?
* stale object fields actively consumed?
* controlled reclaim?
If schedule/object attacker-configurable, repeatably replaced, and stale pointer
goes into nontrivial processing, consider:
* repeatable lifetime manipulation +1;
* structured stale-object leverage +1
ONLY if independent requirements are met.
Do NOT use taprio rule to promote unrelated cleanup/destructor UAFs.
DEVICE / DRIVER / DMA RULES
Privileged kernel/device-management memory corruption path: +1
Apply only when patch establishes corruption of high-value:
* lifetime state;
* page ownership;
* MMU;
* DMA ownership;
* function pointers;
* credentials;
* sensitive descriptors.
Do not award merely because code is in a driver.
RDMA/GPU/ALSA/V4L2 APIs are not high-control merely because userspace can
configure objects.
Require exploitation-relevant influence.
IMPORTANT DRIVER LIFETIME DISTINCTION:
Do NOT classify all driver UAFs alike.
Distinguish:
A. fixed async stale storage:
    teardown
        ->
    old DMA/URB/fixed buffer remains active
        ->
    controller/device later touches same fixed stale storage
from:
B. concrete repeated object lifetime mutation:
    release/put(object)
        ->
    object may be destroyed
        ->
    same reference survives
        ->
    second release/put/refcount mutation on same potentially freed object
Category A may remain constrained under FIXED STALE STORAGE rules.
Category B must be evaluated under CONCRETE REPEATED RELEASE / REFCOUNT SIGNAL
and must not be reduced to ordinary cleanup-only UAF merely because it occurs
inside GPU/display/device code.
BPF PRIVILEGE GATING RULE
For evaluated product, assume BPF/eBPF/XDP is privileged when unprivileged BPF is
disabled by default or loading/attaching requires:
* CAP_BPF;
* CAP_SYS_ADMIN;
* host CAP_NET_ADMIN;
* privileged netns preparation;
* root-controlled sysctl;
* other host-admin setup.

* do NOT award Local unprivileged trigger;
* do NOT award Local unprivileged high-control API;

Likewise:

is preferred over YES when only netdevice stage is known namespace-scoped.

conservative cap = 5
paranoid cap = 6
UNLESS evidence shows:
* true unprivileged trigger;
* working LPE;
* controlled reclaim/replacement;
* arbitrary R/W;
* non-host-root escape;
* page-cache/shared-page corruption;
* meaningful boundary bypass.
IMPORTANT:
This 5/6 is a MAXIMUM, not a TARGET.
Do NOT raise otherwise 3/4 or 4/5 BPF issue merely because caps are 5/6.
For privilege-gated BPF cleanup UAF with crash-only impact and no meaningful
reuse primitive:

paranoid 4-5
are allowed.

Do not award Structured stale-object leverage merely because stale object is

MANDATORY ACTIVE-STATE RETIREMENT / SYNCHRONIZATION BYPASS
Treat a bug as stronger than an ordinary stale-metadata or WARN-only
issue when the patch establishes all of the following:
1. an existing object, mapping, translation, ownership record, or other
   active kernel state is still live;
2. the normal code contains an explicit retirement protocol for replacing
   that state, such as drop, zap, unlink, remove-from-rmap, invalidate,
   synchronize, flush, revoke, or equivalent;
3. the vulnerable special case bypasses that retirement protocol and
   directly installs or activates replacement state;
4. the fix restores the normal retirement operation before replacement;
5. the old state participates in later active kernel operations rather
   than being merely diagnostic or passive metadata.
This is evidence of a concrete active-state lifetime/consistency
violation and may justify a strong CLASS_B signal even when a literal
heap UAF is not yet demonstrated.
Do not reduce such a case to WARN-only solely because the first observed
symptom is WARN_ON.
TRANSLATION-DOMAIN REINTERPRETATION
ACTIVE SEMANTIC / TRANSLATION-DOMAIN TRANSITION: +1
Award +1 when the vulnerable path causes or permits an already-active
translation, mapping, or lookup state to be replaced or reinterpreted as
belonging to a materially different semantic domain WITHOUT first performing
the teardown, invalidation, or retirement required for the old domain.
Examples of materially different domains include:
- normal RAM / memslot-backed mapping -> emulated MMIO / no-slot mapping;
- ordinary memory translation -> special/device translation;
- present translation -> non-present/special encoding where the old present
  state requires explicit retirement;
- one mapping ownership/type domain -> another domain whose bookkeeping,
  lifetime, permissions, or access semantics differ.
Strong indicators:
1. The old mapping/state is already active or visible to execution.
2. The new mapping/state has materially different semantics, not merely a
   different address, PFN, permission bit, or equivalent value.
3. Normal replacement requires explicit teardown, zap, invalidation, drop,
   synchronization, or retirement of the old state.
4. The vulnerable special-case path bypasses or occurs before that normal
   teardown.
5. The fix moves the special-case handling after the old-state teardown,
   or otherwise forces the semantic transition through the normal retirement
   path.
This signal is independent from the base active-state retirement signal:
- active-state retirement scores the failure to retire live old state;
- translation-domain reinterpretation scores the additional fact that the
  stale old state is being carried across a change in semantic meaning or
  translation domain.
Do NOT award merely because:
- a PFN, GFN, address, or PTE changes;
- a mapping is updated normally;
- permissions change without a materially different interpretation domain;
- MMIO, KVM, page tables, or translation machinery are merely involved;
- stale state is possible but no semantic-domain transition is established.
Do NOT infer UAF, arbitrary read/write, guest-to-host escape, C:H/I:H, or LPE
from this signal alone.
This signal normally contributes +1 and should not by itself establish
CLASS_A or Important severity.
ACTIVE TRANSLATION SYNCHRONIZATION SIGNAL
Give additional weight when a security-relevant fix not only removes,
drops, or replaces an active page-table or translation entry, but also
adds or restores a TLB flush, shootdown, MMU notifier synchronization,
RCU grace period, fence, or equivalent mechanism required to prevent
continued use of the old translation/state.
A required remote TLB flush is evidence that stale state may remain
operationally active outside the immediate software data structure.
Do not treat this as proof of arbitrary memory access by itself.
However, when combined with bypassed teardown of a live mapping, it is
a strong unresolved exploitation/availability signal and should normally
increase CLASS_B confidence or ActionableScore.
+1 ACTIVE SEMANTIC DOMAIN TRANSITION
Award +1 when an already-live kernel-managed mapping or object changes
between materially different semantic domains while stale state from
the old domain may survive.
Examples include:
- normal RAM/memslot mapping -> emulated MMIO;
- ordinary mapped page -> no-slot/special mapping;
- one ownership domain -> another;
- normal object representation -> special/sentinel representation.
Requirements:
1. the old state is active/live;
2. the new state has materially different semantics;
3. normal teardown of the old state should occur before replacement;
4. the vulnerable path bypasses that teardown.
Do not award for ordinary value/flag changes with no semantic-domain
transition.
+1 SECONDARY INDEX / REVERSE-MAPPING STALENESS
Award +1 when the patch indicates that replacing or removing active
state must also remove or update a secondary kernel index/reference,
such as:
- reverse map / rmap;
- lookup tree;
- ownership list;
- hash membership;
- page-table tracking entry;
- registration table;
- notifier-visible association;
and the vulnerable path bypasses the normal operation that keeps the
secondary structure synchronized with the primary object/mapping.
This signal is stronger than generic stale metadata because later kernel
walkers may discover and act on the obsolete association.
Do not award if the secondary structure is purely diagnostic or if
continued traversal/use is not plausible from the surrounding code.
AUTHORITATIVE GUEST-TO-HOST FINAL-IMPACT RULE
